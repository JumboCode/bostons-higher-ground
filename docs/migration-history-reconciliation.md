# Migration history reconciliation (0000–0005)

This is a narrowly scoped recovery tool for a database whose application schema already matches cumulative SQL migrations 0000–0005 but whose default Drizzle migration ledger is absent or empty. It records history, never executes migration SQL against the target, and leaves 0006 for the ordinary Drizzle migrator. It is dry-run by default. No production run is supported.

## Prerequisites and protected target

Obtain a disposable Neon child branch cloned from the relevant database, its connection URL, and the protected production endpoint hostname from the project owner. Never substitute a production URL. The tool deliberately ignores `DATABASE_URL` and does not load `.env` files. Provide secrets through your shell's secret mechanism without printing them:

```sh
export BRANCH_DATABASE_URL='<disposable Neon child branch connection URL>'
export RECONCILE_ALLOWED_HOST='<exact child endpoint hostname from that URL>'
export RECONCILE_PRODUCTION_HOST='<production endpoint hostname, without credentials>'
node scripts/reconcile-migration-history.mjs
node scripts/reconcile-migration-history.mjs --apply
node scripts/reconcile-migration-history.mjs
```

The allowed hostname must match exactly, must be a Neon endpoint, and must differ from the protected production endpoint. Pooler/non-pooler variants of the same endpoint are treated as identical for production exclusion. Both endpoint confirmations must be hostnames, not URLs. Only the default/5432 port and `sslmode`/`channel_binding` query parameters are accepted; duplicate parameters and routing overrides such as `host` or `options=endpoint=...` are refused. TLS is normalized to `sslmode=verify-full`. Ambient `PGOPTIONS` is refused, and the client supplies an explicit safe startup search path. These are operator-provided protections, not Neon control-plane proof of branch identity: independently verify the child branch in Neon before running. A mistaken production hostname defeats that protection. This CLI intentionally cannot authorize production use.

Stop application writers, sync workers, deployment jobs, and other migration runners before either mode. The operation takes exclusive locks on the ledger and the eight baseline tables, a transaction-scoped advisory lock shared by this tool, a five-second lock timeout and a thirty-second statement timeout. A normal Drizzle migrator does not take this advisory lock and reads its last migration before opening its migration transaction, so these locks cannot safely coordinate an already-started ordinary migrator. Quiescing all writers/migrators is required. Dry-run also locks tables, temporarily creates a missing ledger, and inserts proposed rows inside a transaction that always rolls back. An apply failure rolls back all changes made by that transaction. PostgreSQL sequence values on a preexisting ledger may advance despite rollback; the tool never relies on contiguous IDs.

## What is accepted

The runtime compares catalog-rendered definitions against `scripts/lib/migration-baseline-0005.json`, generated by executing the historical SQL in isolated PGlite, never in the target database. It checks columns/types/nullability/defaults/collations/identity/generated status, named primary/unique/foreign/check constraints and their validation/deferral, indexes including predicates and validity/readiness, table kind, row security, and absence of user triggers/policies/rewrite rules. The migration ledger receives the same structural validation, including RLS, triggers and rules, and its exact rows are reread after insertion before commit. Extra columns/indexes/constraints on baseline tables are rejected, including `sync_log.skipped_record_ids` from already-applied 0006. Missing tables fail closed. Differences in PostgreSQL catalog rendering between engine versions can produce a conservative refusal: review them; never weaken the comparison just to force acceptance.

Only tables actually created by the SQL history are checked. Snapshot 0005 additionally describes `housing_records`, but none of 0000–0005 creates it; it and other unrelated application tables are outside this reconciliation's scope. The snapshot is therefore used to identify baseline candidates, not treated as authoritative evidence that SQL created every snapshot object. This tool verifies current schema, not historical data transformations or provenance. In particular it cannot prove that the 0005 duplicate-attempt cleanup ran historically; the expected unique running-source index proves the resulting uniqueness invariant.

The manifest pins all six SHA-256 hashes and journal timestamps. At runtime these must equal installed Drizzle `readMigrationFiles` output from the exact local SQL bytes. The installed node-postgres migrator stores these fields in `drizzle.__drizzle_migrations`, and selects pending work by the greatest `created_at`, not by matching hashes. Therefore a partial, corrupted, duplicate or otherwise nonmatching nonempty ledger is refused; it is never patched. An exactly matching six-row ledger is an idempotent no-op. Do not use this tool if a custom migrations schema/table is configured.

Already-applied 0006 requires a separate, reviewed reconciliation; this tool intentionally refuses it. Do not remove the column or rewrite migration history to make this tool pass. A database genuinely missing baseline schema must be provisioned separately, not marked as migrated.

## Validation and next migration on a disposable branch

Local integration checks:

```sh
PGLITE_MODULE=/absolute/path/to/@electric-sql/pglite/dist/index.js node --test tests/migration-history-reconciliation.test.mjs
```

Set `PGLITE_MODULE` (or the existing `SYNC_MIGRATION_PGLITE_MODULE`) to an installed PGlite module path. PGlite is an optional isolated test dependency, not a new application dependency. With neither variable configured, database integration tests skip; the target protection test still runs. No machine-local fallback path is imported. To verify the unconfigured behavior, run `env -u PGLITE_MODULE -u SYNC_MIGRATION_PGLITE_MODULE node --test tests/migration-history-reconciliation.test.mjs`. Tests apply historical SQL only in isolated in-memory databases and check dry-run rollback, exact ledger metadata, idempotency, drift rejection, partial/corrupt history, transaction rollback and target protection. A further integration test runs the installed normal node-postgres Drizzle migrator/session/dialect using a PGlite transport adapter, proves only 0006 is applied, preserves an existing sync row, and verifies a second migrate is a no-op. Real cross-session contention, Neon engine compatibility and live migration behavior still require branch validation.

After a successful branch dry run, capture nonsecret row counts and representative existing baseline/report/sync values, apply reconciliation, and verify those values are preserved. To exercise the installed normal Drizzle migrator on that same disposable branch:

```sh
node --input-type=module <<'JS'
import pg from 'pg';
import { drizzle } from 'drizzle-orm/node-postgres';
import { migrate } from 'drizzle-orm/node-postgres/migrator';
import { validateTarget } from './scripts/lib/migration-history-reconciliation.mjs';
const target = validateTarget(process.env);
const client = new pg.Client({ connectionString: target.toString() });
await client.connect();
try {
  await migrate(drizzle(client), { migrationsFolder: './drizzle' });
  const ledger = await client.query('SELECT created_at FROM drizzle.__drizzle_migrations ORDER BY created_at');
  const column = await client.query("SELECT data_type FROM information_schema.columns WHERE table_schema='public' AND table_name='sync_log' AND column_name='skipped_record_ids'");
  console.log({ migrations: ledger.rows.length, timestamps: ledger.rows.map(r => r.created_at), skippedRecordIdsType: column.rows[0]?.data_type });
} finally { await client.end(); }
JS
```

Expect seven ledger entries, the final timestamp `1794096000000`, and `skippedRecordIdsType: 'jsonb'`. Verify existing rows again and rerun this normal migration command to confirm no further changes. Reconciliation itself will now refuse the 0006 schema as designed. Discard the test branch after review. No Neon branch validation has been performed as part of the local implementation; a branch URL and independent endpoint confirmation remain prerequisites.
